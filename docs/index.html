Conceitos básicos

Clique num cartão para abrir. O de borda vermelha é o mais importante do projeto.

📦Node.js, npm e package.jsono que roda o código e de onde vêm os pacotes

Node.js executa JavaScript fora do navegador: node server/index.js = "rode este arquivo".

npm vem junto com o Node e baixa pacotes (código pronto feito por outras pessoas, como o express).

package.json é a ficha do projeto:

  • dependencies: os pacotes usados. npm install lê a lista e baixa tudo em node_modules/.
  • scripts: atalhos. npm start sobe o servidor; npm run ws roda o teste de eventos.
  • engines: a versão mínima do Node (22.13, por causa do SQLite embutido).

node_modules/ nunca se edita e pode ser apagada e recriada. O package-lock.json guarda as versões exatas, para instalar igual em outro computador.

🧩Módulos: require e module.exportscomo um arquivo usa o outro 
// db.js exporta
module.exports = { createSession, getCurrentSession };

// sessions.js importa
const db = require('../db');          // caminho = arquivo do projeto
const express = require('express');   // nome solto = pacote do node_modules
const fs = require('node:fs');        // "node:" = já vem com o Node

O código "solto" de um módulo roda uma vez só, no primeiro require. Por isso o db.js abre o banco uma única vez, mesmo sendo usado por vários arquivos.

🌐Cliente, servidor, IP e portacomo o iPhone acha o computador

Servidor = programa que fica esperando pedidos. Cliente = quem pede (navegador, curl, iPhone).

IP = endereço do computador na rede (ex.: 192.168.0.10). Porta = qual programa dentro dele (o nosso é a 3000).

localhost = "este mesmo computador", só serve para testar nele mesmo. O servidor escuta em 0.0.0.0 ("aceite de qualquer rede"), e é isso que deixa o iPhone acessar http://IP-do-computador:3000.

JSON é o formato de texto para trocar dados: { "id": "abc", "code": 47 }. API é o conjunto de rotas que o servidor oferece; chamamos de "contrato" porque o app nativo futuro vai depender dela.

📎multipart/form-datacomo uma foto viaja num pedido

JSON não carrega arquivo binário bem. Para mandar foto usamos o formato de formulário multipart: o pedido vai em "partes", uma com o arquivo (file) e outras com textos (sessionId, clientPhotoId).

É o que o curl -F faz. No servidor, quem entende esse formato é o pacote multer.

🚦Express: rotas e middlewarecomo o servidor organiza os pedidos 
app.get('/api/health', (req, res) => res.json({ ok: true }));
//                        ↑ pedido  ↑ resposta

Rota: "quando chegar GET /api/health, rode esta função".

Middleware: função que roda no meio do caminho, antes da rota final. upload.single('file') lê o arquivo e deixa em req.file; express.json() lê o JSON e deixa em req.body. O pedido passa por uma fila de funções, em ordem.

Router: um mini-app montado num prefixo. app.use('/api/photos', router) faz o router.get('/:id') responder em /api/photos/:id. O :id é um parâmetro: req.params.id.

⚡WebSocketpor que o iPad recebe na hora

No HTTP é sempre o cliente que pergunta; o servidor não consegue "ligar" para o iPad. O WebSocket é uma conexão que fica aberta nos dois sentidos: o iPad conecta uma vez em /ws e o servidor empurra mensagens quando quiser.

  • Broadcast: mesma mensagem para todos os conectados.
  • Ping/pong: a cada 30 s o servidor pergunta "está aí?"; quem não responde é desconectado.
  • Reconexão: se cair, o cliente reconecta e busca o que perdeu com GET /api/photos?since=…. O WebSocket avisa; quem guarda a verdade é a API.
🗄️SQLite e SQLo banco de dados em um arquivo

SQLite é um banco que vive num único arquivo (data/db.sqlite), sem instalar nada. Usamos o que vem no Node (node:sqlite). Os dados ficam em tabelas, como planilhas com regras.

CREATE TABLE ...                       -- cria tabela
INSERT INTO photos (...) VALUES (...)  -- adiciona linha
SELECT ... FROM photos WHERE id = ?    -- busca
UPDATE photos SET ... WHERE id = ?     -- altera
  • PRIMARY KEY: identifica a linha (o id).
  • UNIQUE: o banco recusa valores repetidos (usado no client_photo_id).
  • REFERENCES: photos.session_id tem que apontar para uma família que existe.
  • JOIN: junta tabelas numa consulta (traz o code da família junto com a foto).
  • INDEX: um sumário que deixa buscas rápidas.
  • Prepared statement (?): mais rápido e seguro, porque um valor nunca vira comando (evita SQL injection).
  • WAL: modo mais resistente a desligamentos e a leitura + escrita ao mesmo tempo.
🔑UUIDidentificadores sem combinar com ninguém

Um id aleatório como 3f2b9c1e-…, gerado com crypto.randomUUID(). A chance de repetir é praticamente zero, então tanto o servidor quanto o iPhone podem gerar o seu sem perguntar a ninguém.

🛡️Idempotência o mais importantepor que nenhuma foto duplica

Idempotente = fazer várias vezes dá o mesmo resultado que fazer uma vez.

O problema: o iPhone envia, o servidor salva, mas a resposta se perde porque o Wi-Fi piscou. O iPhone acha que falhou e reenvia. Sem cuidado, a foto duplicaria.

A solução: o iPhone cria um clientPhotoId antes de enviar e repete o mesmo em todo reenvio. O servidor:

  1. Já tem foto com esse id? → devolve o mesmo id (200), sem salvar de novo.
  2. Está processando uma com esse id agora? → espera terminar e devolve o mesmo id.
  3. É nova? → salva e devolve id novo (201).

E o UNIQUE no banco é a última barreira.

⏳async / await e Promiseesperar sem travar

Ler arquivo e redimensionar imagem demoram. O Node não fica parado: enquanto uma foto é processada, atende outros pedidos.

  • Promise = "um resultado que vai chegar depois".
  • await = "espere este resultado antes de seguir" (só dentro de função async).
  • Promise.all([a, b]) = faça os dois ao mesmo tempo (display e thumb em paralelo).
  • try { } catch (err) { } = tente; se der erro, trate aqui. finally roda sempre.
🖼️EXIF, HEIC, display e thumbo que acontece com a imagem

EXIF: dados escondidos na foto, incluindo a orientação. O iPhone grava "deitada" e anota "gire 90°"; se ninguém aplicar, fica torta. sharp(...).rotate() aplica de verdade.

HEIC: formato padrão do iPhone; nem todo programa abre, então convertemos para JPEG.

sharp: pacote muito rápido para redimensionar e converter.

Cada foto vira 3 arquivos: original (intocado), display (até 2048 px, para mostrar grande) e thumb (até 400 px, para grades).

📡Bonjour / mDNSachar o servidor sem saber o IP

O servidor "anuncia" no Wi-Fi: "sou um _papainoel._tcp na porta 3000". O futuro app nativo do iPhone escuta e acha o servidor sozinho. Hoje ninguém usa; está pronto para o app nativo (seção 9 do PROJETO.md).

📥Fila offline no iPhone fase 2IndexedDB: por que a foto não se perde sem Wi-Fi

IndexedDB é um banco de dados dentro do navegador, guardado no próprio iPhone. Ao contrário de uma variável, ele sobrevive se a página for fechada ou o iPhone reiniciar.

Quando o fotógrafo tira uma foto, ela primeiro vai para a fila no IndexedDB, já com seu clientPhotoId. Só depois a página tenta enviar. A foto só sai da fila quando o servidor responde 200/201.

  • Sem Wi-Fi? A foto espera na fila e a barra mostra quantas estão guardadas no iPhone.
  • A rede voltou? A fila é enviada sozinha, da mais antiga para a mais nova.
  • Caiu no meio do envio? Ela é reenviada com o mesmo clientPhotoId, e a idempotência do servidor evita duplicata.
🔁Backoff (novas tentativas)tentar de novo sem martelar a rede

Se o envio falha por rede, a página espera e tenta de novo: 1 s, 2 s, 4 s, 8 s… até 30 s entre tentativas. Isso é backoff exponencial: não fica tentando 100 vezes por segundo enquanto o Wi-Fi está fora.

Assim que algo indica que a rede voltou (o teste de conexão a cada 5 s, o WebSocket reconectando, a tela voltando do segundo plano), a espera é cancelada e a fila sai na hora.

Erros definitivos (ex.: 422, imagem ilegível) não são repetidos sozinhos: a foto aparece em "Fotos com erro", com os botões Tentar e Descartar.

🔒http na rede local: o que não funciona"contexto seguro" e suas consequências

Algumas funções do navegador só existem em contexto seguro (https ou localhost). No iPhone acessamos http://IP:3000, então:

  • Sem Service Worker: a página não abre do zero com o servidor desligado. Uma vez aberta, a fila funciona normalmente. Regra no evento: abra a página com o servidor ligado e não recarregue à toa.
  • Sem crypto.randomUUID(): geramos o UUID com crypto.getRandomValues (shared/uuid.js).

O IndexedDB pertence ao endereço: http://192.168.0.10:3000 e http://papainoel.local:3000 têm filas separadas. Use sempre o mesmo endereço, de preferência o IP fixo.

📲PWA e "Adicionar à Tela de Início"a página com cara de app

O manifest (camera/manifest.webmanifest) e as tags apple-mobile-web-app-* dizem ao iPhone o nome, o ícone e que a página deve abrir em tela cheia, sem a barra do Safari.

O ícone é desenhado em SVG (shared/icon.svg), e o servidor gera os PNGs que o iPhone exige (server/icons.js).

Atenção: o app da tela de início tem armazenamento separado do Safari. Escolha um dos dois e use sempre o mesmo.

🖥️Como a vitrine decide o que mostrar fase 3prioridades, tempos e pré-carregamento
  1. A última foto fica na tela: uma foto nova tira o slideshow na hora e fica 1 minuto. Se outra foto nova já estiver esperando, a atual fica só 2,5 s, para uma sequência não criar atraso.
  2. 1 minuto sem foto nova: slideshow embaralhado das últimas 2 horas, 6 s por foto, até a próxima foto chegar.
  3. Sem nenhuma foto: tela de espera. A neve e o fundo vermelho em degradê ficam sempre na página.

Pré-carregamento: a imagem é baixada por inteiro antes de entrar em cena, com transição suave, então não pisca. Se travar, desiste em 15 s e segue para a próxima.

Ocultar da vitrine: a foto sai da tela na hora, mesmo se estiver sendo exibida (pedido do cliente / LGPD).

Sem Wake Lock: essa função que mantém a tela ligada exige contexto seguro, então não existe em http. No iPad, use Bloqueio Automático: Nunca.

🧱Módulos no navegadorimport / export nas páginas

No servidor usamos require; no navegador usamos <script type="module"> com import/export, o formato padrão moderno:

// shared/uuid.js
export function uuid() { ... }

// camera/camera.js
import { uuid } from '../shared/uuid.js';

A pasta public/shared/ guarda o que câmera, vitrine e balcão vão reutilizar.

⚙️Variáveis de ambienteconfigurar sem mexer no código

Valores passados na hora de rodar. PORT=4000 npm start sobe na porta 4000. No código aparecem como process.env.PORT. Também existe DATA_DIR, para guardar os dados em outra pasta.

    Operação no evento

    O que pode dar errado no dia, o que o sistema já resolve e o que depende de cuidado.

    🌐 "Sem internet" é o normal

    Tudo roda na rede do roteador próprio. Se a internet do shopping cair, nada muda.

    🔌 "Perder conexão" é outra coisa

    É o iPhone não conseguir falar com o servidor. Qualquer quebra no caminho iPhone → Wi-Fi → roteador → computador → servidor causa isso. É disso que a fila offline protege.

    O que a fila não resolve

    🔄 Recarregar com o servidor fora

    A página não abre do zero sem servidor (limite do http). As fotos continuam guardadas e saem quando a página abrir de novo.

    🌐 Endereço diferente

    Outro IP, ou .local no lugar do IP, é outra fila. As fotos antigas só saem pelo endereço antigo.

    📵 iPhone perdido ou quebrado

    As fotos tiradas pela página não vão para o rolo da câmera. O que estava na fila se perde. Fique de olho no "✓ Tudo enviado".

    A operação é viável?

    Sim. É a arquitetura comum nesse tipo de evento, não depende de nada externo, e a parte mais delicada (não perder foto) já está resolvida e testada. Os riscos que sobram são de operação e hardware, não de código:

    Decisões tomadas

    O que escolhemos e por quê, para não esquecer.

    💻 Mac ou Windows no evento

    Ainda indefinido. O servidor não usa nada exclusivo de um sistema; o que for específico fica em scripts/ (Fase 5).

    🗄️ node:sqlite

    Já vem no Node, nada para compilar no Windows. No lugar do better-sqlite3. Exige Node ≥ 22.13.

    🔄 heic-convert como plano B

    Substitui o sips (que só existe no Mac). JS puro, roda em qualquer sistema.

    📁 Original sempre guardado

    Nenhuma foto se perde, mesmo se o processamento falhar. A impressão futura usa a melhor qualidade.

    🧭 Caminhos relativos

    No banco, relativos a data/: a pasta pode mudar de lugar ou de computador.

    📅 Código por dia local

    Números curtos ("sou a 47") e o dia não vira às 21h, como aconteceria em UTC. Por isso a coluna extra day.

    1️⃣ Família nº 1 automática

    O iPhone sempre tem uma família válida, mesmo que ninguém aperte "Nova família".

    📷 Câmera nativa via <input>

    Resolução total e funciona em http. Custo: o toque extra em "Usar foto" (o app nativo resolveria).

    📱 Câmera horizontal e simples

    A maioria das fotos é na horizontal, então ela é o padrão. Dois botões meio a meio, "Nova família" (com o código) e "Tirar foto", e uma faixa com as últimas fotos, que confirmam o envio com ⏳ ou ✓. Sem galeria.

    🧾 Balcão sem seleção por enquanto

    Por enquanto, cada clique em "Imprimir 10x15" ou "Imprimir 15x20" imprime uma cópia de uma foto. Cópias e seleção de várias fotos ficam para um próximo passo da Fase 6.

    🚫 Nova família só com conexão

    Criar família exige o servidor (é ele quem numera). Sem conexão o botão fica desativado; as fotos continuam na família atual.

    ⚠️ Erro definitivo não some

    Foto recusada pelo servidor fica no iPhone em "Fotos com erro" até alguém tentar de novo ou descartar (com confirmação).

    📂 Uma pasta por família

    fotos/<dia>/familia-047/ com nomes legíveis: plano B se o balcão falhar. Usa o dia da família, para quem atravessa a meia-noite não se misturar com a 47 do dia seguinte.

    ⏱️ Tempos da vitrine no endereço

    A decisão sobre os tempos ainda está em aberto. Com ?novo=&slide=&horas=, dá para ajustar no dia sem mexer no código.

    🖱️ Dois cliques nos dois sistemas

    O supervisor é escrito em Node e serve para Mac e Windows; os arquivos de início só o chamam. Assim, o sistema do evento pode ser decidido depois. Iniciar ao ligar o computador fica para quando ele for definido.

    💾 Backup pendente

    Fica para o futuro, junto com o HD externo. Até lá, se o disco do computador falhar, as fotos se perdem.

    🌐 Um endereço só

    A fila pertence ao endereço (IP vs. .local, Safari vs. tela de início). No evento: sempre o mesmo, de preferência o IP fixo.

    🖨️ Impressão aos poucos

    A impressora é a Kodak 305 e, por enquanto, a impressão é só no Windows. O balcão pede ao servidor, que manda direto para a Kodak, sem diálogo, em 10x15 ou 15x20. A foto preenche a folha, como no app da Kodak: no 10x15 corta cerca de 7% em cima e embaixo.
